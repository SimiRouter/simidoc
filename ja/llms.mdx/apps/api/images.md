# 画像

まず **API プロトコル**を選び、次に実現したい **効果** を決め、最後に **サイズ・品質・形式・枚数** を確認します。プロトコルはリクエストとレスポンスの構造を決め、効果はモデルの能力とプロンプトで決まり、仕様は出力要件を決めます。この三つを混同しないでください。

生成と編集は画像を返します。画像理解は画像を入力し、テキストまたは構造化結果を返します。通常のテキストモデルは画像パラメータを追加しても画像生成能力を得ません。呼び出す前に[モデルと料金](https://api.dwchainless.com/ja/pricing/)で正確なモデル ID、API 対応、課金グループ、クォータを確認してください。実際のリクエストで料金が発生する場合があります。

## 概要

| やりたいこと         | 入力                 | 出力              | 代表的なエンドポイント                   |
| -------------- | ------------------ | --------------- | ----------------------------- |
| テキストから画像を生成    | プロンプト              | 新しい画像           | `POST /v1/images/generations` |
| 既存の画像を変更       | プロンプト + 1 枚以上の参考画像 | 編集後の画像          | `POST /v1/images/edits`       |
| 会話しながら画像を生成    | 会話メッセージ + 画像ツール    | 画像とテキストの混合結果    | `POST /v1/responses`          |
| モデルに画像を見て答えさせる | 画像 + 質問            | テキスト（新しい画像ではない） | `POST /v1/chat/completions`   |

## 中核となる概念

まず三種類の数値を区別すると、以降のパラメータと料金が理解できます。

* **ピクセル寸法**：実際の幅 × 高さで、例えば `1024x1024` です。ファイルの実解像度を決めるもので、ファイル容量ではなく、品質区分とも異なります。
* **アスペクト比**：`1:1`、`16:9`、`9:16` などの比率で、画角の形だけを決めます。同じ比率でも複数のピクセル寸法があり、比率だけでは出力サイズを指定したことになりません。
* **解像度区分**：`1K`、`2K`、`4K` などの区分です。ベンダーのネイティブ区分は長辺または製品ラインで定義され、当サイトの画像単位課金区分は長辺で分類されます。名称が同じでも境界は一致するとは限らず、相互に推測できません。

よくある誤解が三つあります。`quality` はレンダリング品質を制御するもので、圧縮品質ではありません。PNG、JPEG、WebP はファイル形式で、拡張子を変えても形式は変換されません。Base64 と URL は受け渡し方法にすぎず、解像度ではありません。項目ごとの対応は後述の「4. 画像仕様と課金」を参照してください。

## 1. 各種 API：プロトコルで選ぶ

三つのプロトコルにはそれぞれ独立したリクエストパラメータ、レスポンスパラメータ、例があります。スクリプト呼び出し、エージェント利用、結果の保存と失敗処理も各プロトコルで説明しているため、OpenAI 専用の汎用チュートリアルを先に読む必要はありません。

| ------------------- | ------------------------ | ----------------------------------------------------- | ---------------------------------------------- | ------------------------------------------- |
| OpenAI              | テキストから画像生成               | `POST /v1/images/generations`                         | `data[].b64_json`、互換モデルは URL を返す場合もある          | [生成](/simidoc/ja/apps/api/images/openai/generations)                  |
| OpenAI              | 画像編集 / 画像から画像生成          | `POST /v1/images/edits`                               | 編集後の画像                                         | [編集](/simidoc/ja/apps/api/images/openai/edits)                        |

| xAI Grok            | テキストから画像生成 / 複数枚生成       | `POST /v1/images/generations`                         | `data[].url` または `data[].b64_json`             | [生成](/simidoc/ja/apps/api/images/grok)                                |
| BFL FLUX            | テキストから画像生成 / 参考画像生成（非同期） | `POST /v1/flux-pro-1.1` など                            | 先に `polling_url` を取得し、完了後に `result.sample` を取得 | [生成](/simidoc/ja/apps/api/images/flux)                                |

**通義千問のこのセクションは Qwen ネイティブのリクエスト本文を使用し、当サイトのゲートウェイの `/v1/images/generations` と `/v1/images/edits` 経由で呼び出し、返却は統一して `data[]` です。** 本文を OpenAI の `prompt` フィールドに書き換えないでください。モデル ID には当サイトのチャネルが実際に提供する名称を使用してください。即夢は Volcengine Ark ネイティブのリクエスト本文を使用し、Grok はパスが OpenAI Images と同じですが画角パラメータが `aspect_ratio` と `resolution` に変わり、FLUX は同期で画像を出さず、先にタスクを送信して `polling_url` をポーリングする必要があります。三者は互いにフィールドを流用できません。

呼び出し方法もプロトコルごとに異なります。OpenAI Images の通常リクエストは完全な結果を待ち、対応モデルのみ画像イベントストリームを使用できます。Gemini のストリーミングは `streamGenerateContent?alt=sse` を使用し、本ディレクトリの通義千問と即夢の例は同期返却を使用します。Grok は既定で同期で、`deferred` により遅延タスクにもできます。FLUX は固定で非同期ポーリングです。いずれも「非同期」パラメータを追加するだけで汎用タスクキューにはなりません。具体的なリクエスト、出力、完了判定は [OpenAI](/simidoc/ja/apps/api/images/openai)、[Gemini](/simidoc/ja/apps/api/images/gemini)、[通義千問](/simidoc/ja/apps/api/images/qwen)、[即夢](/simidoc/ja/apps/api/images/jimeng)、[Grok](/simidoc/ja/apps/api/images/grok)、[FLUX](/simidoc/ja/apps/api/images/flux)の各説明を参照してください。

## 2. 各種効果：目的で選ぶ

「水彩」「背景変更」「商品合成」などは通常、生成または編集のタスクであり、それぞれ独立した API ではありません。以下はタスク分類であり、全モデルの能力保証ではありません。対応範囲は該当するプロトコルとモデルの説明で確認してください。

| 実現したい効果                     | 入力とプロンプトの要点                      | インターフェースの選択と制限                                               |
| --------------------------- | -------------------------------- | ------------------------------------------------------------ |
| ゼロからの制作：イラスト、表紙、ポスター、写実的な画面 | 主体、構図、スタイル、光、表示する文字を記述           | テキストからの画像生成を選ぶ。文字と細部は要確認                                     |
| 参考画像のバリエーション：主体や構図を引き継いで再生成 | 参考画像を提供し、保持する項目と変更する項目を個別に説明     | 画像編集 / 画像から画像生成を選ぶ。ピクセル単位の保持は保証されない                          |
| スタイル変換：写真を水彩や線画などに変換        | 参考画像に目標スタイルを加え、主体と配置を保持するか説明     | 参考画像対応の編集モデルを選ぶ                                              |
| 背景の置換、要素の追加・削除、部分修正         | 変更領域を明示し、対応時はマスクを提供              | 編集インターフェースを選ぶ。マスクの対応と規則はモデルごとに変わる                            |
| 複数画像の合成：商品、人物、シーンの合成        | 各参考画像の用途、主体間の関係、最終的な配置を指定        | 複数画像入力対応の編集モデルを選び、画像枚数の上限を確認                                 |
| 複数ターンの反復：前の画像を元に修正を続ける      | プロトコルが要求する履歴内容または参照情報を保持         | 複数ターンの画像作業に対応するインターフェースを選ぶ。テキストを保存しただけで画像コンテキストが残ると仮定してはならない |
| 透明背景の素材                     | 白背景や市松模様ではなく、真の透明チャネルが必要であることを明示 | モデルが対応する場合に限り、透明背景と透明チャネルを保持できる出力形式を選ぶ                       |
| 画像認識、文字抽出、図表への質問            | 画像を入力し、分析目的を説明                   | 画像理解インターフェースを選ぶ。編集後の画像ではなくテキストを返す                            |

これらの能力と制限は [OpenAI 画像生成](https\://developers.openai.com/api/docs/guides/image-generation)、[Gemini 画像生成と編集](https\://ai.google.dev/gemini-api/docs/image-generation)、[Qwen 画像編集](https\://www.alibabacloud.com/help/en/model-studio/qwen-image-edit-api)を参照してください。公式の例は、現在のゲートウェイのチャネルが同じ能力を開放していることを意味しません。

## 3. 呼び出し：4 ステップで最初の 1 枚

どのプロトコルを選んでも、呼び出しは同じ順序に従います。設定を確認し、エンドポイントを選び、最小リクエストを送信し、結果を読み取って検証します。以下は一般的な流れのみを説明します。具体的なフィールドは該当するプロトコルのページに従ってください。

### 1. リクエスト URL、キー、モデルを確認する

* **リクエスト URL**：当サイトのゲートウェイは `https://api.dwchainless.com` で、エンドポイントのパスはプロトコルと操作によって変わります。
* **キー**：[API キー管理](https://api.dwchainless.com/keys)で作成し、リクエスト時に `Authorization: Bearer $API_KEY` で付与します。プロンプト、ソースコード、スクリーンショット、Git に書き込まないでください。
* **モデル**：[モデルと料金](https://api.dwchainless.com/ja/pricing/)から完全なモデル ID をコピーし、対象エンドポイントに対応していることを確認します。生成、編集、画像理解は別々のモデルが提供する場合があります。

### 2. エンドポイントとリクエスト形式を選ぶ

上のプロトコル表に従ってエンドポイントを選び、リクエスト本文の形式を確認します。

| 操作              | エンドポイント（OpenAI 形式）            | リクエスト形式                       |
| --------------- | ----------------------------- | ----------------------------- |
| テキストから画像生成      | `POST /v1/images/generations` | JSON                          |
| 画像編集 / 画像から画像生成 | `POST /v1/images/edits`       | JSON `images[]` または multipart |
| 対話型画像生成         | `POST /v1/responses`          | JSON、画像ツールを有効化                |
| 画像理解            | `POST /v1/chat/completions`   | JSON、コンテンツ項目に `image_url` を含む |

Gemini、通義千問、即夢、Grok、FLUX はそれぞれのネイティブなリクエストフィールドを使用します。OpenAI のフィールドをそのまま流用することはできません。

### 3. 最小リクエストを送信する

最初の呼び出しでは 1 枚だけを生成し、ストリーミングを使用せず、認証、モデル、パラメータが有効であることを確認します。以下は OpenAI の画像生成の例です。

```bash
API_URL="https://api.dwchainless.com/v1/images/generations"
API_KEY="PASTE_API_KEY_HERE"
curl "$API_URL" \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-image-2",
    "prompt": "一只小机器人在图书馆阅读，水彩插画，不要文字。",
    "n": 1,
    "size": "1024x1024",
    "output_format": "png"
  }'
```

返却が正常であることを確認してから、必要に応じて `n` を増やし、サイズを調整するかストリーミングを有効にします。完全な多言語の例は[生成](/simidoc/ja/apps/api/images/openai/generations)と[編集](/simidoc/ja/apps/api/images/openai/edits)を参照してください。

**返却形態（イメージ）**：実際のレスポンスの Base64 は非常に長いため、ここでは先頭のみを示します。成功時は HTTP 200 だけでなく `data[]` を確認してください。

```json
{
  "created": 1763366400,
  "data": [{ "b64_json": "iVBORw0KGgoAAAANSUhEUg..." }],
  "usage": { "input_tokens": 28, "output_tokens": 4160, "total_tokens": 4188 }
}
```

### 4. 結果を読み取って検証する

1. **状態を確認**：2xx のみがリクエスト成功です。4xx ではパラメータと権限を確認し、5xx やタイムアウトではリクエストが実行済みかどうかを先に確認します。
2. **結果を読み取る**：`data[]` から画像を取得します。GPT Image は `data[].b64_json` を返し、互換モデルは `data[].url` を返す場合があります。必ず先頭項目があると仮定しないでください。
3. **画像を保存**：Base64 はまずバイナリにデコードし、実際の MIME タイプに応じて拡張子を選びます。URL は速やかにダウンロードし、ダウンロード時に API キーを付与しないでください。
4. **検証**：ファイルが開けるか、実際のピクセル寸法、透明効果、内容を確認し、使用ログを照合します。HTTP 200、空の `data[]`、ストリーミング中の中間プレビューはいずれも最終画像が保存済みであることを意味しません。

## 4. 画像仕様と課金

### リクエストの各仕様が制御するもの

| 仕様     | 意味と例                                          | 混同しやすい点                                                         |
| ------ | --------------------------------------------- | --------------------------------------------------------------- |
| ピクセル寸法 | 実際の幅 × 高さ、例えば `1024x1024`、`1536x1024`         | ファイル容量ではなく、自動的に品質区分を意味するものでもない                                  |
| アスペクト比 | `1:1` は正方形、`16:9` は横長、`9:16` は縦長              | 同じ比率でも複数の解像度があり得る。比率だけでは全ピクセル寸法を指定できない                          |
| 解像度区分  | 一部のモデルは `1K`、`2K`、`4K` などのネイティブパラメータを使用       | ベンダー区分の実際の幅と高さはモデルと比率にも依存し、当サイトの画像単位課金のピクセル境界と直接同一視すべきではない      |
| 生成品質   | 例えば OpenAI の `quality` は、モデルのレンダリング品質の選択を制御する | `size` ではなく、JPEG/WebP の圧縮品質でもない。モデルによっては同名のパラメータがない場合がある        |
| ファイル形式 | PNG、JPEG、WebP など。実際に返却される MIME タイプに従う         | Base64 と URL は受け渡し方法であり、画像形式ではない。拡張子を変えても形式は変換されない              |
| 透明背景   | 画像に透明チャネルが含まれ、素材の重ね合わせに適する                    | モデル、パラメータ、ファイル形式のすべてが対応する必要がある。「透明背景」と書いても結果に必ず透明チャネルが含まれる保証はない |
| 枚数     | 生成数または候補数。フィールドと上限はプロトコルとモデルによって変わる           | プロンプトに「3 枚生成」と書くことは API の枚数設定とは異なる。複数画像の入力も複数画像の出力とは異なる         |

同じアスペクト比では、辺の長さを 2 倍にすると総ピクセル数は 4 倍になりますが、画面の細部や鮮明さが同じ倍率で向上する保証はありません。選択時はまず利用シーンを満たし、次にモデルの対応、所要時間、価格を確認してください。必ずしも最高の区分を使う必要はありません。

具体的なフィールド、利用可能な値、コード例は [OpenAI リクエスト形式](/simidoc/ja/apps/api/images/openai/generations)、[Gemini リクエスト形式](/simidoc/ja/apps/api/images/gemini/generate)、[通義千問リクエスト形式](/simidoc/ja/apps/api/images/qwen/generations)、[即夢リクエスト形式](/simidoc/ja/apps/api/images/jimeng)、[Grok リクエスト形式](/simidoc/ja/apps/api/images/grok)、[FLUX リクエスト形式](/simidoc/ja/apps/api/images/flux)を参照してください。OpenAI の出力品質、形式、透明パラメータは[公式の出力設定](https\://developers.openai.com/api/docs/guides/image-generation#customize-image-output)を、Qwen のサイズと出力要件は[公式の仕様](https\://www.alibabacloud.com/help/en/model-studio/qwen-image-api)を参照してください。あるプロトコルのパラメータを別のプロトコルにそのままコピーしないでください。

### 当サイトの 1K、2K、4K 画像単位課金の違い

[モデル価格](https://api.dwchainless.com/ja/pricing/)で 1K / 2K / 4K の三区分の画像単位課金が明示されているモデルにのみ、下表が適用されます。Token 課金やその他の固定単価のモデルはそれぞれの規則で精算され、「画像モデル」という名称だけで課金方式を判断することはできません。

| 課金区分 | 長辺                        | 寸法例（ピクセル）           |
| ---- | ------------------------- | ------------------- |
| 1K   | 両辺とも ≤ 1024 ピクセル          | 1024×1024           |
| 2K   | 長辺が > 1024 かつ ≤ 2048 ピクセル | 1280×720、1536×1024  |
| 4K   | いずれかの辺が > 2048 ピクセル       | 2560×1440、3840×2160 |

**合計価格 = 現在の区分の 1 枚あたり価格 × 課金枚数。** 完了結果による精算に対応するインターフェースは実際の完了枚数で課金され、ストリーミング中の中間プレビューは完了画像に数えません。1 枚あたりの価格、グループ、最終的な請求は現在のモデル価格と使用ログに従い、本ページでは価格数値を固定しません。

上記の三区分の画像単位ルールを採用する場合、他の有効なサイズ区分が指定されていないときに限り、`size` を省略するか `auto` を使用するとデフォルトで 1K 区分として課金されます。明示的に指定したネイティブ解像度フィールドは引き続き課金区分を決めます。次の境界で分類します。1K は両辺とも ≤ 1024、2K は長辺が > 1024 かつ ≤ 2048、4K はいずれかの辺が > 2048 です。例えば `1280x720` は 2K に属し、`2560x1440` は 4K に属します。

**課金区分は出力寸法の保証ではありません。** Gemini の `generationConfig.imageConfig.imageSize` はモデルのネイティブ解像度の選択であり、実際のピクセル寸法はモデルと比率を合わせて確認する必要があります。当サイトは対応しているリクエストフィールドに基づいて課金区分を計算し、それによって統一された出力の幅と高さを保証するものではありません。互いに矛盾するサイズフィールドを同時に記入せず、画像単位のルールを公式の直接接続や Token 課金モデルに適用しないでください。

### よく使う比率の早見表：14 種類の比率 × 1K / 2K / 4K

### size の正しい 3 つの書き方

一部の OpenAI 互換ゲートウェイは以下の書き方に対応しています。フィールドが有効かどうかはモデルとチャネルによって異なり、対応していない場合は明示的なピクセルに戻してください。

| 書き方          | リクエスト断片                            | 用途                          |
| :----------- | :--------------------------------- | :-------------------------- |
| 明示的なピクセル（推奨） | `{"size":"1536x2048"}`             | 最も直感的で、プリセット換算の差異を避けられる     |
| 比率 + 解像度     | `{"size":"3:4","resolution":"2k"}` | 2K / 3\:4 のプリセットで換算         |
| 自動サイズ        | `{"size":"auto"}`                  | モデルが能力に応じて選択し、固定の幅と高さを約束しない |

* K 区分は `resolution` に、`size` にはピクセルまたは比率を記入します。`2k` を `size` に書き込まないでください。
* 寸法の区切りには小文字の英字 `x` を使用し、乗算記号 ×、大文字 X、配列、乗算記号を含む文字列を使用しないでください。
* 比率を `size` に書き込んだ場合は独立した `aspect_ratio` より優先され、明示的なピクセルまたは `auto` は比率プリセットより優先されます。
* OpenAI 公式の gpt-image-2 の任意サイズの上限は 3840×2160 です。`1:4`、`4:1` の 4K の組み合わせはこの上限を超えるため、片辺の上限超過と表示しています。他のモデルの上限はモデルの説明に従ってください。
* Gemini と Qwen はそれぞれ独自のサイズフィールドを使用するため、上記の書き方をそのまま適用することはできません。
