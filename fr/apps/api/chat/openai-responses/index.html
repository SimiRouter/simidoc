Responses API

Traiter uniformément texte typé, entrées multimodales, appels d’outils et événements en streaming.

Description de l’interface

POST /v1/responses utilise des éléments d’entrée et de sortie plutôt que la structure choices/message de Chat, pour les outils, le multimodal et les sorties structurées.

Adresse d’intégration : https://api.dwchainless.com, avec l’en-tête Authorization: Bearer $SIMIROUTER_API_KEY. L’API directe officielle OpenAI est https://api.openai.com. Authentification : Bearer avec une clé OpenAI. Choisissez un modèle accessible au compte et prenant en charge la capacité voulue.

La passerelle fournit la création de réponses, mais pas d’interface générale GET /v1/responses/{id} ni d’annulation. Le fonctionnement asynchrone natif OpenAI avec background: true ne s’applique donc pas à cette intégration ; utilisez le mode synchrone ou SSE. Les tâches en arrière-plan nécessitent une connexion officielle directe offrant création, consultation et annulation.

Démarrage rapide

  1. Préparer la configuration : créez une clé dans Gestion des clés API et copiez depuis Modèles et prix un ID de modèle complet compatible avec Responses.
  2. Envoyer une requête minimale : passez un court texte comme input et laissez stream à false ; vérifiez d’abord l’authentification, le modèle et les paramètres.
  3. Lire le résultat : la requête réussit uniquement si HTTP est 2xx et status vaut completed ; le texte se trouve dans l’élément output[].content[] où type=output_text.
  4. Valider : contrôlez error, incomplete_details et le contenu réel, puis vérifiez les journaux d’utilisation.

Remplacez PASTE_API_KEY_HERE et MODEL_ID par des valeurs réelles ; une fois validé, ajoutez des outils, une sortie structurée, ou activez le streaming.

Paramètres de requête

Le type de contenu est application/json.

ChampTypeObligatoireDescription
modelstringOuiObligatoire via la passerelle ; choisissez un modèle acceptant Responses.
inputstring / arrayConditionnelTexte ou liste d’éléments d’entrée ; une génération ordinaire exige une entrée, éventuellement avec un historique disponible.
input[].rolestringConditionnelRôle du message : user, assistant, system ou developer.
input[].content[].typestringConditionnelÉléments de contenu typés comme input_text, input_image ou input_file.
input[].content[].textstringConditionnelTexte lorsque type=input_text.
input[].content[].image_urlstringConditionnelURL d’image ou data URL lorsque type=input_image.
input[].content[].file_data / file_url / file_idstringConditionnelChoisissez une seule source lorsque type=input_file ; voir Compréhension de fichiers.
instructionsstringNonInstructions prioritaires ; avec previous_response_id, fournissez de nouveau les instructions nécessaires.
max_output_tokensintegerNonLimite totale des tokens de sortie, raisonnement compris.
streambooleanNontrue renvoie un flux SSE avec types d’événements.
previous_response_idstringNonID de la réponse précédente ; dépend de la conservation amont et d’un contexte accessible commun. Ne pas combiner avec conversation.
conversationstring / objectNonObjet ou ID de conversation ; ne peut pas être combiné avec previous_response_id. La disponibilité dépend du canal.
storebooleanNonDemande à l’amont de conserver la réponse ; ne contrôle pas les journaux de la passerelle.
tools / tool_choicearray / string or objectNonFonctions ou outils intégrés du fournisseur et règles de sélection.
parallel_tool_callsbooleanNonAutorise ou non plusieurs appels de fonctions dans une réponse.
reasoningobjectNonLes modèles de raisonnement compatibles peuvent configurer effort et summary ; les valeurs varient selon le modèle.
text.formatobjectNonFormat de texte, par exemple type=json_schema ; différent de response_format dans Chat.

truncationstringNonDéprécié par OpenAI ; préférez context_management. disabled (défaut) renvoie une erreur si le contexte est trop long, auto peut en supprimer une partie. La prise en charge dépend du comportement réel de la passerelle.
includearrayNonDonnées supplémentaires demandées, par exemple reasoning.encrypted_content et web_search_call.action.sources.

Omettez les champs facultatifs non définis. stop, enable_thinking et autres extensions de compatibilité ne sont pas des champs standard OpenAI Responses. reasoning_content n’est pas non plus un champ de sortie standard ; le raisonnement utilise des éléments reasoning distincts et ne garantit pas l’exposition de la chaîne de pensée interne.

Exemple de requête

Valeur de retour

Une réussite sans streaming renvoie HTTP 200. Les principaux champs sont présentés ci-dessous ; les champs d’état facultatifs inutilisés peuvent être null.

ChampTypeDescription
id / objectstringID de réponse ; object=response.
created_at / modelinteger / stringHeure de création (secondes Unix) et modèle.
statusstringcompleted, incomplete, failed, queued, in_progress ou cancelled ; ces états peuvent apparaître en streaming comme en arrière-plan.
output[]arrayÉléments de sortie typés, pouvant mêler message, reasoning, function_call, web_search_call, etc. ; ne lisez pas systématiquement output[0].
output[].type / id / statusstringType, ID et état de l’élément de sortie, selon son type.
output[].rolestringLe rôle de sortie d’un message est généralement assistant.
output[].content[]arrayÉléments de contenu : type=output_text pour le texte, type=refusal pour un refus.
output[].content[].text / annotationsstring / arrayTexte et annotations, notamment les citations.
output[].call_id / name / argumentsstringID de corrélation, nom de fonction et arguments sous forme de chaîne JSON de function_call.
errorobject / nullInformations d’échec ; généralement null en cas de réussite complète.
incomplete_detailsobject / nullRaison d’incomplétude, par exemple max_output_tokens ; ne pas assimiler à une réussite complète.
usage.input_tokens / output_tokens / total_tokensintegerTokens d’entrée, de sortie et totaux.
usage.*_tokens_detailsobjectDétails facultatifs d’utilisation, notamment cache et raisonnement.

Pour extraire le texte, parcourez output et sélectionnez les éléments type=message, puis concaténez les text de leurs content sous type=output_text. La propriété SDK output_text est une agrégation pratique, pas un champ nécessairement présent dans le JSON REST brut.

Réponse en streaming

Avec stream=true, analysez les SSE selon event et data : response.created crée la réponse ; response.output_text.delta ajoute du texte ; response.output_item.added/done gère les éléments ; response.function_call_arguments.delta assemble les arguments d’outils. Une réponse n’est complète qu’après response.completed et vérification du response.status final ; traitez séparément response.failed, response.incomplete et error. Une simple fin de connexion réseau ne prouve pas la réussite.

Exemples de code

Définissez SIMIROUTER_API_KEY, SIMIROUTER_MODEL ; SIMIROUTER_BASE_URL permet de remplacer l’adresse de la passerelle par défaut ; n’y ajoutez pas /v1. Les exemples Python 3, Node.js 18+ et Go utilisent uniquement la bibliothèque standard. L’exemple curl fait encoder le JSON de façon sûre par Python 3.

Codes d’erreur

Statut HTTPSignification ou type d’erreur du fournisseurTraitement
400Requête invalideVérifiez les champs obligatoires, le JSON, les paramètres du modèle et la longueur du contexte.
401Échec de l’authentificationVérifiez que la clé est présente, valide et rattachée au bon compte.
403 / 404Accès interdit / ressource introuvableVérifiez les autorisations du modèle, l’ID de ressource et l’URL.
429Limite de débit ou de quotaDistinguez limitation de débit et crédit insuffisant à l’aide du corps de réponse ; réessayer ne résout pas un manque de crédit.
500 / 503Erreur de service / indisponibilité temporaireConservez l’identifiant de requête et limitez les nouvelles tentatives avec attente progressive aux erreurs temporaires.

Les erreurs natives OpenAI contiennent généralement error.message, error.type, error.param, error.code ; param, code peuvent être null ; ne supposez pas que ces champs existent toujours ou correspondent au code HTTP. La passerelle peut renvoyer une erreur d’authentification, de routage ou de quota avant que la requête atteigne le fournisseur ; le seul code HTTP ne permet pas d’attribuer l’erreur à l’amont. Même avec HTTP 200, vérifiez status, error et incomplete_details ; un événement SSE d’échec ne modifie pas forcément le code HTTP déjà envoyé.

Les réponses longues et les requêtes en streaming peuvent durer de plusieurs dizaines de secondes à plusieurs minutes ; configurez un délai d’attente suffisant et, en cas de coupure, jugez à partir des deltas reçus et du motif d’arrêt plutôt que de renvoyer automatiquement. Pour 429 et 5xx, examinez d’abord le corps de la réponse et les journaux d’utilisation ; en cas de refus par la politique de contenu, modifiez le prompt ou l’entrée au lieu de réessayer à l’identique.
